# 技术架构说明

## 1. 目标

这个项目的目标不是做一个只会演示的 RAG demo，而是做一套你可以长期维护、可部署、可持续演进的个人知识库。

架构设计遵循三个原则：

- 优先保证导入、检索、管理三条主链路稳定
- 优先保留可维护性和可排障性
- 优先选择适合个人项目的简单方案，而不是过早平台化

## 2. 核心选型

### 后端

- `FastAPI`
- 原因：接口定义清晰，文档自动生成，适合文档导入、检索和问答 API

### 向量库

- `Qdrant`
- 原因：Docker 部署方便，适合个人项目，也保留后续升级混合检索的空间

### 前端

- `Streamlit`
- 原因：开发速度快，适合构建知识工作台，并快速验证产品链路是否真正可用

### 模型接入

- OpenAI 或兼容 OpenAI API 的服务
- 原因：便于快速接入稳定模型能力，不要求第一版就自建推理服务

## 3. 系统流程

### 导入流程

1. 文档进入 `data/raw/` 或通过 Web 上传
2. `document_loader.py` 负责解析文本
3. `chunking.py` 按设定的 chunk 大小和 overlap 切块
4. `embeddings.py` 调用 embedding 接口生成向量
5. `vector_store.py` 将 chunk 和 metadata 写入 Qdrant
6. 重复导入同一路径文件时，旧索引会先被清理，再写入新索引

### 查询流程

1. 用户在 Streamlit 工作台中输入问题
2. 后端生成查询向量
3. 从 Qdrant 召回候选 chunk
4. 进行轻量关键词重排
5. 将上下文拼接后发送给大模型
6. 返回答案、引用片段和调试信息

### 管理流程

1. 聚合磁盘文件与向量索引
2. 识别四种状态：已索引、待索引、孤立索引、外部索引
3. 支持按文件删除原文、索引或两者

## 4. 目录职责

### `app/api`

- 对外提供健康检查、文档管理、导入、查询等接口

### `app/services`

- `document_loader.py`：文档解析
- `chunking.py`：文本分块
- `embeddings.py`：embedding 调用
- `vector_store.py`：Qdrant 读写与聚合
- `rag_service.py`：RAG 编排逻辑

### `ui`

- 提供操作工作台，串联系统概览、问答、导入、上传、文档治理

### `scripts`

- 提供批量导入入口，适合初始化或脚本化同步

## 5. 当前架构优点

- 学习和维护成本较低
- 本地开发和 Docker 环境接近
- 业务链路集中，出问题时排障路径清晰
- 后续可平滑替换检索层、UI 层或模型层

## 6. 后续升级方向

### 检索能力升级

- 更强的 reranker
- 稀疏检索或混合检索
- 更细粒度的 metadata 过滤

### 数据源升级

- 网页抓取
- Notion / Obsidian 同步
- OCR PDF

### 产品化升级

- 历史会话
- 收藏回答
- 标签体系
- 登录鉴权与多用户隔离

## 7. 维护建议

- 统一把原始资料归档到固定目录
- 定期批量导入新增文件
- 回答不准时先检查 chunk、metadata 和过滤条件
- 任何结构改动都同步更新 README 和部署文档

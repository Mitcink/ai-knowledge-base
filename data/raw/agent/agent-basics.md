# Agent 快速入门

本文是这个知识库的第一篇基础文档，用来回答三个问题：

- Agent 到底是什么
- 它和普通 LLM 有什么区别
- 从工程角度，怎么搭出一个最小可运行 Agent

## 1. Agent 是什么

Agent 可以理解为“带有目标驱动、工具能力和执行闭环的大模型系统”。

和只做一次输入输出的普通 LLM 不同，Agent 通常具备这些能力：

- 理解目标：不是只回答一句话，而是知道要完成什么任务
- 规划步骤：把复杂任务拆成若干子任务
- 调用工具：使用 API、数据库、浏览器、代码执行环境等外部能力
- 维护状态：保存上下文、结果、中间变量或记忆
- 执行闭环：根据观察结果继续思考、继续行动，直到完成或终止

一句更工程化的定义是：

> Agent = `LLM + Tools + State + Control Loop + Guardrails`

## 2. 为什么 LLM 需要 Agent 化

普通 LLM 很强，但它天然有边界：

- 不能直接操作外部系统
- 不能稳定完成多步任务
- 不能自动验证结果是否正确
- 不能天然维护长期状态
- 对复杂目标容易“一次答完，但并没有真正做完”

Agent 化的本质不是“让模型更聪明”，而是给模型增加执行能力和控制结构，让它从“会说”走向“会做”。

## 3. Agent 的最小架构

一个最小可运行 Agent 通常包含五部分：

### 3.1 模型

负责理解任务、做决策、决定下一步该调用什么工具或输出什么结果。

### 3.2 工具

工具是 Agent 的外部执行器，常见包括：

- 搜索或检索
- 数据库查询
- 代码执行
- 浏览器操作
- 调用业务 API
- 发送消息或写入系统

### 3.3 状态

状态用于保存：

- 用户目标
- 历史对话
- 工具调用结果
- 当前计划
- 中间产物

### 3.4 控制循环

控制循环决定 Agent 如何持续运行。典型模式是：

1. 读取当前状态
2. 分析下一步
3. 选择工具或直接回答
4. 执行动作
5. 写回结果
6. 判断是否继续

### 3.5 约束与护栏

护栏用于避免失控，包括：

- 最大步数
- 工具白名单
- 权限控制
- 输出格式约束
- 失败重试上限
- 人工确认节点

## 4. 最常见的 Agent Loop

很多 Agent 框架本质上都在实现类似循环：

```text
Goal -> Think -> Act -> Observe -> Update State -> Decide Next Step -> End or Continue
```

这类循环常被叫作 ReAct 风格，核心思想不是“链路一定复杂”，而是让模型在推理和行动之间交替进行。

## 5. 一个最小单 Agent 的搭建步骤

如果你想从 0 到 1 自己实现，不要一开始就上重框架，先按下面四步做。

### 步骤 1：定义任务边界

先明确：

- 这个 Agent 解决什么问题
- 它能调用哪些工具
- 它绝对不能做什么
- 完成任务的判定标准是什么

### 步骤 2：设计工具接口

每个工具都应该有清晰的输入输出，不要把“万能函数”塞给模型。

好的工具设计通常满足：

- 职责单一
- 参数明确
- 结果结构化
- 错误可感知

### 步骤 3：定义状态与循环

至少要定义：

- 当前目标
- 当前步骤
- 历史动作
- 工具结果
- 终止条件

### 步骤 4：加入基础护栏

最少要有：

- `max_steps`
- `allowed_tools`
- 失败兜底输出
- 超时处理

## 6. 一个极简伪代码

```python
state = {
    "goal": user_goal,
    "history": [],
    "steps": 0,
}

while state["steps"] < max_steps:
    decision = llm_decide(state, tools_schema)

    if decision["type"] == "final":
        return decision["answer"]

    if decision["type"] == "tool_call":
        result = run_tool(decision["tool"], decision["args"])
        state["history"].append({
            "action": decision,
            "result": result,
        })
        state["steps"] += 1
        continue

return "未在限制步数内完成任务"
```

这段逻辑虽然简单，但已经具备 Agent 的核心骨架。

## 7. 典型应用场景

Agent 适合的不是所有问题，而是这些类型的问题：

- 需要多步决策
- 需要调用外部工具
- 需要跨系统操作
- 需要根据中间结果动态调整策略

常见场景包括：

- 智能客服工单分流
- 数据分析与报表生成
- 浏览器自动化
- 运维巡检与故障定位
- 代码生成与仓库操作

## 8. 常见误区

### 误区 1：把 Agent 等同于“更长的 Prompt”

错。Prompt 只是其中一层，真正让 Agent 成立的是工具、状态和控制循环。

### 误区 2：用了框架就等于理解了 Agent

错。框架只是封装。先理解控制结构，再选框架。

### 误区 3：工具越多越强

错。工具越多，决策空间越大，错误率和维护成本也会升高。

### 误区 4：能跑通 demo 就算完成

错。真正难的是稳定性、评测、权限、回归和可维护性。

## 9. 你现在最适合做的第一步

如果你要边学边搭，建议先实现一个最小单 Agent：

- 一个模型
- 两个工具
- 一个状态对象
- 一个 `while` 循环
- 一个 `max_steps`

不要急着上多 Agent，也不要先做复杂 UI。先把最小闭环跑通，再讨论 Skill、Hook、Harness、Loop 的工程化问题。

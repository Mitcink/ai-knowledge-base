# Prompt 与上下文工程

本文聚焦 Agent 开发里最容易被低估的一层：不是“写几句提示词”，而是设计一套模型能稳定遵循的输入协议。

最后核对日期：2026-07-26

## 1. 定义与边界

Prompt 工程解决的是“模型如何理解任务”，上下文工程解决的是“模型在当前这一步到底看到了什么”。对 Agent 来说，二者必须一起设计。

一个可维护的 Agent Prompt 通常至少包含：

- 身份与职责
- 当前目标
- 可用工具及调用边界
- 输出格式约束
- 成功判定标准
- 失败时的兜底行为

如果 Prompt 只描述任务、不描述工具边界和终止条件，Agent 往往会出现“会说但不会收敛”的问题。

## 2. 核心原理

### 2.1 把高优先级约束放到明确的位置

OpenAI 当前文档明确区分了 `instructions` 与 `input`。高层规则应放在 `instructions` 或更高优先级消息里，而不是埋在用户输入正文中。

工程建议：

- 把长期稳定规则放在系统/开发者层
- 把当前任务目标放在本轮输入层
- 把示例和格式协议单独分段
- 不要把运行时状态和长期规范混写在一个大段落里

### 2.2 让 Prompt 像接口文档，而不是像散文

Prompt 最稳定的写法不是“更像人话”，而是“更像协议”：

- 用标题分段
- 用字段名标出输入
- 明确允许和禁止行为
- 给出 1 到 2 个高质量示例

Few-shot 示例适合教模型学“输出形状”和“决策风格”，不适合塞入大量业务背景。

### 2.3 上下文必须按步骤裁剪

Agent 不是一次性大问答。每一步看到的上下文都应该围绕“当前节点要做什么”来裁剪。

典型做法：

- 规划节点只看目标、约束、已知事实
- 工具选择节点只看可用工具、参数模式、最近结果
- 最终回答节点只看已经确认的结果和引用材料

不要把完整历史、完整检索结果、完整日志全部塞回每一步。

## 3. 常见结构模板

### 3.1 决策型 Prompt

适合分类、路由、是否调用工具的判断。

建议结构：

1. 角色
2. 决策目标
3. 可选动作列表
4. 决策标准
5. 输出 JSON 结构
6. 少量示例

### 3.2 工具调用型 Prompt

适合“看完状态后决定是否调工具、调哪个工具、传什么参数”。

建议结构：

1. 当前任务目标
2. 工具清单
3. 每个工具的适用条件
4. 禁止调用条件
5. 调用后下一步怎么判断

### 3.3 结果整合型 Prompt

适合把检索结果、工具结果和状态汇总成最终输出。

建议结构：

1. 目标读者
2. 可引用事实来源
3. 不确定时的表达方式
4. 输出格式
5. 禁止编造规则

## 4. 工程落地方式

### 4.1 把 Prompt 版本化

不要把 Prompt 只写在代码字符串里。至少要做到：

- 独立文件存储
- 有版本号或日期
- 关联适用节点
- 关联最近一次评测结论

### 4.2 把运行时上下文做成显式装配

建议把上下文拼装拆成代码层函数，例如：

- `build_planner_context(state)`
- `build_tool_context(state, tool_specs)`
- `build_final_answer_context(state, evidence)`

这样做的收益是可测试、可审计、可压缩。

### 4.3 优先约束输出结构

若下游要消费结果，优先让模型输出结构化 JSON、字段化 Markdown 或 schema 约束结果，而不是自由文本。

## 5. 常见错误与避坑

### 5.1 把 Prompt 变成需求文档堆积区

表现：

- 一段超长规则
- 没有优先级
- 没有步骤边界

后果是模型会忽略后半段，或者在冲突指令中选择不稳定路径。

### 5.2 示例太多但不代表真实任务

示例应该覆盖边界情况，不是为了“显得完整”。错误示例会比没有示例更糟。

### 5.3 把工具协议写得太模糊

不要只写“必要时调用工具”。应写清：

- 什么时候必须调
- 什么时候禁止调
- 调完如何判断结果可用

### 5.4 把长上下文当成记忆方案

长上下文不是记忆系统。它只是一种昂贵、脆弱、容易分心的上下文注入方式。

## 6. 最小实践建议

从单 Agent 起步时，Prompt 层至少做到这四件事：

1. 用固定模板拆分身份、目标、工具、输出
2. 给工具节点单独写 Prompt，不复用聊天 Prompt
3. 把最终回答和中间决策分开建模
4. 每次改 Prompt 后跑一次固定样例回归
